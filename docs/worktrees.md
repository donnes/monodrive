# Worktrees

`monodrive-core`'s `worktrees` reads a Git repository's worktrees and one worktree's changes by running git. Git stays the authority: Monodrive keeps no copy of what `git worktree list` says, only the repositories the user or an agent registered. Nothing here fetches, takes Git's locks, runs hooks, starts the index or walks the disk.

## Which git

`Git::find` takes the first `git` on `PATH`, then `/opt/homebrew/bin/git`, then `/usr/local/bin/git`. The window, opened from the Dock, gets launchd's `PATH`, which has only `/usr/bin`, so the fixed folders let it find the same git as an MCP server started from a terminal. `/usr/bin/git` is skipped during that search and comes last, only when `xcode-select -p` names a developer folder holding git. Without Xcode or the Command Line Tools it isn't git but a shim that opens the installer, so Monodrive reports that Git isn't installed instead of running it. Listing needs git 2.36 or later, for `worktree list -z`; an older git's error passes through.

## How git runs

Each command gets an argument vector, never a shell, and an environment of Monodrive's own: `HOME`, `XDG_CONFIG_HOME` and `DEVELOPER_DIR` from Monodrive's, so the user's global config and ignores apply, and nothing else, so a `GIT_DIR` from the caller can't point git at another repository. On top of that, `GIT_OPTIONAL_LOCKS=0`, so `git status` reads the index without refreshing it or taking `index.lock` under another git, `GIT_TERMINAL_PROMPT=0`, `LANG=C`, `--no-pager` and `core.fsmonitor=false`, so a status never starts a monitor daemon in the user's repository.

A command gets 10 seconds by default, and `worktree_status` takes `timeout_seconds`. Monodrive reads up to 8 MB of output and 64 KB of errors. When git runs out of time or prints more, Monodrive kills the git it started, only that process, and reaps it. Output, errors and exit all arrive as events under one deadline, so a process git started that keeps its error pipe open after git fails can't hold the call past it either. A thread waits for the child with `waitid(WNOWAIT)`, which leaves it unreaped, so its pid can't go to another process before the kill.

## Repositories and states

A repository is known by its common Git folder, through `rev-parse --git-common-dir`, past any links. The repository, a folder inside it, a link to it, its `.git` folder and each of its worktrees all resolve to the same one, so registering or listing through any of them gives one repository. A registration saves that folder and the main worktree's path, or the bare repository's, to show. Loading registrations runs no git: one whose common folder is gone or lost its `HEAD` is unavailable, not an error. Forgetting one removes only the bookmark.

`git worktree list --porcelain -z` gives each worktree's path, HEAD, branch or detached, bare, and Git's locked and prunable notes, with their reasons. Its first entry is the main worktree, or the bare repository. Each worktree's folder is then checked: missing when it's gone, perhaps on a drive that isn't connected; stale when it's there but its `.git` is gone or leads nowhere; replaced when its `.git` leads to another Git folder than this worktree's; unreadable when it can't be looked into. A linked worktree's `.git` file has to name the folder Git keeps for it under the common folder's `worktrees/`, and that folder's `gitdir` file has to name the `.git` back. The main worktree's `.git` has to be the common folder. Those link files are opened without waiting for a writer and must be regular files, and Monodrive reads at most 64 KB of each, so a FIFO or a huge file in their place makes the worktree unreadable instead of hanging or filling memory. Git itself only checks that a `.git` exists there, so it reports a worktree whose folder now holds another repository as fine. Prunable is what Git would prune, and never means a folder is safe to delete: Git calls a worktree it can't look into prunable, and a locked worktree on an unplugged drive is missing but not prunable.

Status runs `git status --porcelain=v2 -z --branch --untracked-files=normal --ignore-submodules=dirty` for one worktree, on demand, and counts staged, unstaged, conflicted and untracked paths. Ahead and behind come from `branch.ab`, which git prints only when the upstream's ref is already here, so they're unknown until it's fetched, and Monodrive never fetches.

## What status could run

`git status` hashes each tracked file whose times differ from the index, and runs the file's clean filter to do it, `filter.<name>.clean` or `.process`. A repository's own config can name any command there, so status first reads `git config --list --show-scope -z`, which runs nothing, and refuses when a local or worktree scope gives a filter a clean or process command: "This repository's own config sets filters that run commands (name), so Monodrive skipped status." Listing still works. Filters from the user's global or system config, such as Git LFS's, run as they do for every git command the user types. A repository can choose one of those for its files through `.gitattributes`, but can't change what it runs.

`--ignore-submodules=dirty` compares a submodule by its commit only. Without it, status runs git inside each submodule, under the submodule's own config and filters. A submodule with a new commit still counts as unstaged; edits inside one don't.

Checked with a fixture whose commands write a marker file, using Monodrive's flags and environment. Under them, status runs none of these: a local `core.fsmonitor` command, `core.hooksPath` hooks including `post-index-change`, `diff.external`, `diff.<driver>.textconv`, `filter.<name>.smudge`, and `core.untrackedCache`. Turning off `core.fsmonitor=false` runs the fsmonitor command, `GIT_OPTIONAL_LOCKS=1` runs `post-index-change`, and leaving out `--ignore-submodules=dirty` runs the submodule's clean filter. The marker test fails if any of the three is removed.
