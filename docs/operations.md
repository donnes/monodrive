# File operations

The window and each `monodrive mcp` server are separate processes, and an agent's MCP server exits with its session. Undo has to work across them: the window can undo what an agent did after the agent has gone. So one process owns every file change, and everything else asks it.

## The owner

`monodrive ops` is a hidden subcommand of the same binary. A client that can't connect starts it detached, in its own process group with `/` as its folder, waits for it to print `ready`, and connects. A `starting.lock` flock keeps two clients from starting two owners at once.

- **State.** `~/Library/Application Support/Monodrive/ops/`, mode 0700, holds the socket, the journal and the locks.
- **Ownership.** The owner holds an exclusive flock on `owner.lock` for its whole life. A second owner fails to take it and exits.
- **Authentication.** Clients connect over the Unix socket `owner.sock`. The owner checks each peer's uid with `getpeereid` and drops connections from other users.
- **Protocol.** One JSON line each way: a `Submission` (request id, origin, typed `Request`) and a `Result<Outcome, String>`. An error means nothing changed.
- **Lifetime.** Clients keep their connection open; the window connects on its first change, paste or undo, when the copies and moves popover opens, or when the journal changes; an MCP server connects on its first change. The window hears the journal change through a kqueue watch on the file and its folder, which reads nothing and keeps no owner running. The owner exits once its last client has disconnected and no job is queued or running, or 30 seconds after starting if none connects. A job thread wakes the poll loop through a socket pair when it ends. The owner never starts the search index.
- **Requests and jobs.** The poll loop answers one request at a time. Trash, rename, batch rename, new items, duplicate, undo and redo run to the end before the reply. Copy, move, compress and extract become jobs: the reply is the job's id at once, and at most two jobs run at a time, each on its own thread, so status and other requests keep being answered. Disk work happens outside the engine's lock; only journal writes and job state take it.

## The journal

`journal.jsonl` is JSON lines, synced after each line. A crash mid-append leaves a last line without its newline, which startup cuts off before appending; any other line that doesn't read stops the owner with an error instead of being skipped. Each operation writes a `Begin` record before anything on disk changes, naming each item by device and inode with where it is and where it's going. It writes an `End` record with the per-item outcome after the changes are made.

- **Retries.** A client that loses its connection resends the same request id. A request id the journal has finished returns its recorded outcome instead of running again.
- **Crashes.** On startup, an operation with a `Begin` and no `End` is settled from the disk. Each item is looked for, by inode, where it was and where it was going, including the volume's Trash. The owner records what it finds as an interrupted outcome and never repeats a rename or a removal. An interrupted creation or copy can't be told from one the user made, so it's reported and left out of the history.
- **Retention.** Past 1,000 finished operations, startup trims the journal to the newest 500, along with the records of any older job continued among them. Undo reaches back no further, and an item emptied from the Trash can't be put back.

## Copy and move jobs

A job's items run one at a time. A job records each source's inode when it's accepted. When an item starts it revalidates its source and destination folder, refuses a source that's a different item than the one queued, and refuses to copy or move a folder into itself.

- **Conflicts.** When the name is taken, the request's choice applies: keep both ("name 2"), replace, skip, or stop. Monodrive never asks, and MCP defaults to stop. Stop leaves the job waiting; continuing it with another choice runs the rest. Replace moves what was there to the Trash before the new item takes its place, and refuses if it can't, or if what's there is the source or holds it. That's compared by identity, along the source's real folders and, when the source is a link, along what it leads to, so a link or a name in another case can't hide it.
- **Moves.** On one volume a move is a rename that never replaces. Across volumes it's a copy, then the source goes to the Trash. If the source changed during the copy or can't be trashed, it stays where it was and the item says so.
- **Copies.** A copy is made under a hidden name in the destination folder (`.monodrive-<job>-<item>`) with `copyfile`, cloning on APFS and keeping metadata and ACLs. Its item count and bytes are checked against the source, and the source against its stamp. Only then is it renamed into place, so a partial copy never sits at the destination. A copy that fails or is cancelled partway goes to the Trash, and the item names where.
- **Progress and cancel.** Jobs report items done and bytes copied; `copyfile`'s callback updates the bytes during a copy and stops it on cancel. Cancel stops after or during the current item and keeps every item already finished. A queued job that's cancelled never starts, and a waiting one ends where it stopped.
- **States.** queued, running, waiting (stopped at a conflict), completed, failed, cancelled, and interrupted.
- **Journal.** A `Job` record holds what was asked. Each item writes a `Work` record before each change it makes and after: the change it's about to make (trash what's in the way, put the copy or the item in place, trash the source), then that it's made. A `Finish` record ends the job, and its changes become one entry in the undo history. A `Continue` record queues a stopped job again with its conflict choice.
- **Crashes.** On startup, a job without a `Finish` is interrupted. For each item partway through, Monodrive looks for each recorded change by inode and keeps what happened, sends an unfinished hidden copy to the Trash, and repeats nothing. An item whose changes all happened counts as done.
- **Continue.** Answering a waiting job, or retrying one that failed, was interrupted or was cancelled, continues the same job under the same id, optionally with another conflict choice. Finished items, and items that stopped partway, stay as they are; the items that changed nothing run again. Each run's changes are their own entry in the undo history, so undo takes back the answer before what came before it. A crash during a continued run is settled like any other. Owners before this retried a job as a new one; loading such a journal drops the old job, whose changes are already in the history.
- **In the window.** A ring at the right of the title bar shows while a job, the window's or an agent's, is queued, running, waiting for an answer or failed, with a dot when one waits or failed. Its popover (⌥⌘J) lists those jobs with Cancel, Skip, Keep Both, Replace or Retry. The window asks the owner for jobs when the journal changes, then about once a second only while a job is queued or running or the popover is open. A failed or finished job shows only if its latest run was queued after the window opened, whether or not a check saw it running. A finished one leaves the list a few seconds later; a failed one stays until it's continued or dismissed. A paste that stops at a name opens the popover; an agent's only marks the ring.

## Undo and redo

The history is linear and shared: undo reverses the newest operation still done, whoever made it, and a new operation drops what could be redone. The window's toasts offer Undo of their own operation by id, which the owner refuses if anything else was done since; ⌘Z undoes the newest. Undo runs an operation's changes last first, and redo first to last. Each item an operation moved toggles between two places: a path, or the Trash. An item an operation created waits in the Trash while that operation is undone, so undoing New Folder, Duplicate or a copy trashes the item and redo puts it back. Undoing a replace also puts back what was replaced. Undoing a move across volumes trashes the copy and puts the source back from the Trash. New Folder with Selection is one operation: undo moves the items back out and trashes the folder in one step.

Before undo or redo changes anything, it checks every item: the same inode is where the operation left it, nothing else occupies the place it's going, and the item hasn't been modified since Monodrive last moved or made it. A folder's stamp covers everything inside it (entry count, total size, latest mtime), so moving a large folder walks it. Any mismatch refuses the whole step with the path and reason. An operation's own moves into or out of a folder it made restamp that folder, so they don't count as edits to it. Renames use `renamex_np` with `RENAME_EXCL`, so a change made between the check and the rename still can't be overwritten.

## Batch rename

`rename::Plan` works out a batch from an ordered list of paths and a rule, reading the disk and changing nothing, so the window and `rename_preview` show the same table. A rule replaces text before the extension (or in the whole name), or formats a name with a number counted in the list's order. A folder has no extension unless it's a package. Each row is ok, unchanged, invalid (empty, `/`, over 255 characters, unreadable) or a collision: with an item outside the batch, with a batch item that keeps its name, or with another row's new name, compared as APFS compares names: whatever their Unicode normalization, and ignoring case where the volume does.

The owner works the plan out again when it runs. With the window's fingerprint (each path's inode and stamp, its new name, and which rows were ok), any difference refuses the whole batch. Problems refuse it too, unless `skip_problems` runs only the ok rows. Items are renamed one at a time and each reports its own result; undo reverses those that were renamed.

A rename into a name another item of the same operation still holds waits for that item to leave. In a cycle (a to b, b to a), the first item parks at a hidden `.monodrive-<op>-<step>` name in its folder until its place is free; an item whose name only changes case parks too, since a volume that ignores case may not rename it in place. Undo and redo route their renames the same way. A parked item that can't take its new name goes back to its old one, after the operation's items that took that name since are moved back. The `Begin` record lists the parked names, so after a crash the owner does the same: back to the old name, on to the new one, or back after moving the rest of its cycle back, before settling the rest. If something else took a name meanwhile and none of that works, the item stays at its hidden name, and its step records that name, so undo brings it back once its old name is free.

## Archives

`archives` reads ZIP archives itself, from the central directory, so listing extracts nothing and loads at most 200,000 entries; past that it says how many it left out and extraction refuses. Names show as stored. The `zip` crate only writes archives, deflate only.

- **Compress** is a job of one item: the selection, all from one folder, becomes "name.zip" for one item or "Archive.zip" for more, beside it, numbered when taken. Folders go in whole with their permissions and modification times (to the second, in an extended timestamp). Links are stored as links, never followed. Sockets, pipes and devices hold no data and are left out; extended attributes and resource forks aren't kept.
- **Extract** makes an item per selected entry or folder, or per top-level name for all of it, in an explicit folder, under its own name. Conflicts work as for copies, and the archive is never replaced or changed.
- **Before the job.** An extraction is refused whole, naming the entries, when one it takes is encrypted, uses a method other than stored or deflate, or has an absolute path or `..`. It's refused when it needs more than the destination's free space, or when the archive claims to expand by more than 1,100 times its size: deflate can't pass about 1,032, so more means entries share data, as zip bombs do. Nothing falls back to another tool.
- **Writing.** Each item is extracted into its hidden name and renamed into place, like a copy. Two entries that are one path once extracted (`a` and `./a`, whatever their Unicode normalization, and where the volume ignores case, `B.txt` and `b.txt` or `σ` and `ς`, by Unicode's full case folding) refuse the item before anything is written. A pair that check misses still fails the item when `O_EXCL` finds the name taken. Every folder is opened with `openat` and `O_NOFOLLOW` and every file created with `O_EXCL`, so nothing is written through a link, whether the archive made it or it was there.
- **Links** may only point down into their own folder: relative, with no `..` anywhere in the target. Then no chain of links can climb, whatever their names, so the check never has to compare names as APFS does. Absolute targets and links at the top of an item, which would lead among the destination's own items, aren't made either. A refused link fails its item, so an archive with `../` links, such as one of `node_modules`, extracts only the items without them. An entry that holds more than it claims stops when it passes that, and each must match its CRC. Folders get their permissions and times last, deepest first. A failed, cancelled or interrupted item's hidden folder goes to the Trash, and the item says where; finished items stay, and undo trashes them.

## Comparison copies

`compare::compare` reads only metadata, so a comparison never claims two files are equal until `verify` has read them. `Comparison::plan` turns selected differences into a one-way copy: what's only on the left, and a differing file or link whose left copy is newer. It checks each item against what the comparison found, then `Request::CopyPlanned` carries each source's identity and stamp, and those of what it replaces. The owner runs it as one copy job whose items each have their own folder. An item whose source or destination no longer matches is refused, not copied or replaced. A replaced item goes to the Trash as for any copy, and only while it's still the item and stamp the plan named. An agent's preview prints a token for the plan, and confirming runs that kept plan, never one made again. Nothing only on the right is ever deleted. The comparison reads a folder only on the left as one item, so edits inside it count from the plan on.

## Trash

Items go to the Trash through `NSFileManager trashItemAtURL:resultingItemURL:`, and the returned location is recorded for put back. A volume without a Trash fails the item; nothing falls back to permanent deletion. Without Full Disk Access, macOS can refuse to read the Trash, and the error passes through to the user or agent.

Empty Trash is the one permanent erase. The window lists what's in `~/.Trash`, asks the person to confirm that many items in its own card (↩ empties, Esc cancels), and sends each item's path with its device and inode. The owner erases an item only if it's still that same item directly in the Trash, and refuses everything if the Trash folder is no longer a real folder (a link would lead the erase elsewhere). Anything trashed after the count, even under a counted name, stays and is reported as skipped. It's journaled like any operation but joins no history, since nothing can undo it. The owner refuses it from agents whatever the Agents setting says, and no MCP tool asks for it: agents can trash, but only a person erases. Volumes' own Trashes aren't emptied, because reading an unbrowsed external or network volume can raise a privacy prompt.

## Agents

Agent requests carry `Origin::Agent` with the name the MCP client gave at `initialize`, if any. The person behind an agent isn't known, so it isn't recorded. The owner reads `agents_change_files` from `settings.json` at each agent request and refuses every agent change, undo and redo included, while it's off. It's on by default. This setting controls a feature; it isn't a security boundary. Any process running as the user can edit the settings file.
